# Android 常见面试题精选

## 1. 请介绍安卓四大组件分别是什么，并说明各自的适用场景。

Android 的四大组件分别是：**Activity**、**Service**、**BroadcastReceiver**、**ContentProvider**。

### Activity —— 界面组件

负责与用户交互的可视化界面。

#### **Activity 的生命周期**

- `onCreate()`：**创建**。生命周期的起点，用于初始化资源（加载布局、绑定事件）。
- `onStart()`：**启动**。应用已创建，界面可见但无法交互（未获取焦点）。
- `onResume()`：**恢复**。应用处于前台，用户可完全交互。
- `onPause()`：**暂停**。失去焦点但仍可见（如弹出非全屏 Dialog）。应保存关键数据，停止动画。
- `onStop()`：**停止**。完全不可见。应释放重量级资源（如网络连接、传感器）。
- `onDestroy()`：**销毁**。生命周期终点。释放所有剩余资源，防止内存泄漏。

#### **Fragment 的生命周期**

Fragment 依附于 Activity，其生命周期更加精细：

- `onAttach`：与 Activity 建立关联。
- `onCreate`：初始化 Fragment 数据。
- `onCreateView`：**创建视图**（加载布局文件）。
- `onViewCreated`：视图创建完毕，常在此初始化 View。
- `onStart`：可见。
- `onResume`：可交互。
- `onPause`：失去焦点。
- `onStop`：不可见。
- `onDestroyView`：**销毁视图**（与 onCreateView 对应）。
- `onDestroy`：销毁 Fragment 实例。
- `onDetach`：与 Activity 解除关联。

### Service —— 后台组件

用于执行后台任务，无界面。适合长时间运行或无需用户交互的工作（如音乐播放、文件下载、轮询）。

- **启动型 (`startService`)**：启动后在该组件后台无限期运行，需手动停止。
- **绑定型 (`bindService`)**：与其他组件绑定，随绑定组件销毁而销毁，支持 IPC 通信。

### BroadcastReceiver —— 广播接收器

用于接收系统或应用发送的广播消息。

- **系统广播**：网络变化、电量不足、开机启动、屏幕亮灭。
- **应用广播**：组件间解耦通信。

### ContentProvider —— 数据共享组件

用于跨应用进程共享数据，统一数据访问接口。

- **场景**：读取系统通讯录、短信、相册，或将自己的数据库暴露给其他 App 访问。

## 2. 你知道安卓中有哪些持久化数据的方案？

Android 常见持久化方案按量级（从轻到重）分类如下：

### 轻量级键值存储

- **SharedPreferences**：老牌方案，基于 XML，存在性能瓶颈（ANR 风险）。
- **DataStore (Preferences)**：Jetpack 新一代组件，基于 Kotlin 协程和 Flow，异步安全，替代 SP。
- **MMKV**（第三方）：腾讯开源，基于 mmap 内存映射，读写性能极高。

### 结构化存储

- **DataStore (Proto)**：基于 Protobuf，类型安全，适合存储复杂的配置对象。

### 数据库存储

- **SQLite**：原生嵌入式关系型数据库。
- **Room**：Google 官方 ORM 库，对 SQLite 的封装，支持编译时检查和 LiveData/Flow 观察。

### 文件存储

- **File**：普通文件存储（文本/JSON/图片/媒体文件）。
- **Cache**：缓存体系（DiskLruCache / OkHttp Cache / Glide Disk Cache），虽属于缓存，但本质也是落地的文件。

## 3. 你同时用过 Java 和 Kotlin，认为 Kotlin 相比于 Java 有哪些优势？

Kotlin 是 Google 推荐的 Android 首选语言，相比 Java 更安全、简洁、现代。

### 核心优势

1. **空安全 (Null Safety)**：编译期处理空指针，大幅减少 `NullPointerException`。
2. **代码简洁**：没有啰嗦的 Getter/Setter，数据类 (`data class`) 一行搞定。
3. **协程 (Coroutines)**：用同步代码的思维写异步，解决回调地狱，轻量级线程。
4. **扩展函数**：无需继承即可扩展类也是功能，取代了繁琐的 `UserUtils` 工具类。
5. **语法糖**：高阶函数、Lambda 表达式更自然，支持默认参数和命名参数。

### 劣势/注意点

- **编译速度**：Clean build 通常比 Java 略慢。
- **学习成本**：语法特性多，扩展函数和作用域函数（`let/apply/run`）如果滥用会导致代码可读性下降。

## 4. 你是否熟悉 MVVM 架构？请介绍该架构的核心设计思路。

**MVVM (Model-View-ViewModel)** 是一种分层架构模式。

### 核心目的

**UI 与 业务逻辑解耦**。实现数据驱动视图，提高代码的可维护性、可测试性。

### 角色分工

- **Model (数据层)**：负责数据获取与处理。包括网络请求 (Retrofit)、本地数据库 (Room)、数据转换。
- **View (视图层)**：Activity / Fragment / Compose。**只负责展示数据和响应用户交互**，不包含业务逻辑。
- **ViewModel (桥梁)**：
- 持有并管理 UI 状态 (`State`)。
- 处理业务逻辑，调用 Repository。
- **生命周期感知**：屏幕旋转时不会销毁，数据依然保留。
- **无 View 引用**：不持有 Activity/Fragment 引用，避免内存泄漏。

### 数据流向

> Model ➡ ViewModel ➡ View

1. **单向数据流**：数据从 Model 流向 ViewModel，ViewModel 将数据转化为 UI State 暴露给 View。
2. **观察者模式**：View 订阅观察 (Observe) ViewModel 中的数据变化（LiveData/StateFlow），数据变动自动刷新 UI。

## 5. LiveData 和 StateFlow 的区别

这是面试中的高频考点，主要区别在于 **生命周期感知** 和 **流的特性**。

| 特性             | LiveData                                                               | StateFlow (Kotlin Flow)                                                              |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **归属**         | Android Jetpack (androidx.lifecycle)                                   | Kotlin 协程库 (kotlinx.coroutines)                                                   |
| **生命周期感知** | **自动感知**。View 处于活跃状态才分发数据，Destroy 时自动解绑。        | **不自动感知**。需要在 View 层配合 `repeatOnLifecycle` 或 `flowWithLifecycle` 使用。 |
| **初始值**       | 不需要初始值。                                                         | **必须有初始值** (StateFlow 是热流)。                                                |
| **线程安全**     | 只能在主线程更新 (`setValue`)，子线程需用 `postValue` (有丢数据风险)。 | 线程安全，可在任何协程上下文中通过 `emit` 或 `value` 更新。                          |
| **防抖特性**     | 默认支持（相同的值重复 setValue 不会通知观察者）。                     | 默认支持（Distinct，值相同时不发射）。                                               |
| **推荐场景**     | 简单的 UI 数据绑定，Java 项目兼容。                                    | **推荐首选**。适合复杂的异步流处理，与 Domain 层/Data 层 Flow 无缝衔接。             |

**总结**：在纯 Kotlin 的现代 Android 开发中，**推荐使用 StateFlow 替代 LiveData**，因为它属于 Kotlin 语言层面，更独立于 Android 平台，且能更好地利用协程生态。

## 6. 安卓 Activity 的四种启动模式分别是什么？各自的适用场景是什么？

- **standard（默认）**：每次 startActivity() 都会创建一个新的实例，可以存在多个相同 Activity 实例，入栈方式：总是压入当前 Task 栈顶
- **singleTop**：如果目标 Activity 已经在栈顶，不会创建新实例，而是复用当前实例，回调 onNewIntent()，如果不在栈顶 → 仍然会创建新实例
- **singleTask**：整个 Task 中只能有一个实例，如果已存在：会把它上面的 Activity 全部出栈回调 onNewIntent()如果不存在：创建新实例
- **singleInstance**：独占一个 Task，该 Task 里只能有这一个 Activity，其他 Activity 会进入别的 Task，不允许同栈混合

## 7. Kotlin 协程的底层原理是什么

Kotlin 协程的底层原理，本质上是编译器把 suspend 函数转换成基于 Continuation 的状态机。协程本身不是线程，它最终还是运行在线程上，只是它可以在挂起点保存当前执行状态和局部变量，而不是阻塞线程。挂起后线程可以去执行其他任务，等异步结果回来后，再通过 Continuation 的 resumeWith 恢复执行。协程切换到哪个线程运行，由 CoroutineDispatcher 决定，比如 Main、IO、Default。也就是说，协程的核心不是“开新线程”，而是“用状态机 + continuation 实现轻量级的挂起恢复和任务调度”。

## 8. 讲一下你对 Handler 的理解

Handler 是 Android 基于消息循环实现的线程调度/线程通信工具，用来把 Runnable 或 Message 投递到指定线程执行。其核心组成与职责是 Lopper：每个有消息循环的线程会有一个 Lopper，它负责不断的从队列取消息并分发执行，MessageQueue：消息/任务的队列，负责按时间顺序排队，Message：消息载体（what,arg1,arg2,obj,data），Handler：对外接口负责把 Runnable/Message 放进队列，以及在合适的时机处理他们。
post 和 sendMessage 的区别：post 传递的是 Runnable，sendMessage 传递的是 Message,Message 会在 handleMessage()里统一分发处理。

> 当 Handler 持有的任务（Message / Runnable）在消息队列里还没执行，但 Handler 持有了外部对象（比如 Activity），导致 Activity 无法被 GC 回收。此时会导致内存泄漏。

## 9. 断点续传和断点下载如何实现的思路

- 断点下载：服务器支持按字节范围下载，客户端可以告诉服务端当前下载的节点，然后从当前的位置继续传，同时把文件写到一个临时的目录里面，而不是一个完整的文件。下次重新下载的时候，先取本地已经下载的大小，然后带着这个偏移量去请求服务端，服务端从指定的位置继续返回数据，客户端再把新数据追加到原来的临时文件。文件下载完成重新命名成一个新的文件。
- 断点续传：上传的时候分片上传，可以把文件分块比如 10MB，20MB，每成功一次服务端就会记录这个分片已经上传完成，客户端本地也会记录，然后恢复的时候，客户端会问服务端哪些分片已经上传了，然后只补传没有完成的分片，接着服务端会把所有的分片文件合成一个新的文件。

## 10. 内存泄漏和内存溢出

- 内存泄漏：某些对象已经没用了，但因为仍然被引用着，垃圾回收器（GC）没法回收它。通过不要让长生命周期对象持有短生命周期对象，单例尽量用 ApplicationContext，页面销毁时候即使释放 View，Adapter，Bitmap 引用等优化。
- 内存溢出：程序在申请新内存时，系统已经分配不出来了。通过压缩图片，按需加载，不要一次性加载超大数据，控制缓存大小，及时释放不用等大对象，避免频繁创建大量的临时对象。

## 13. ANR 异常

ANR 是应用无响应，当主线程堵塞太久就会引发 ANR，其主要原因就是在主线程做耗时操作，比如网络请求，数据库大查询，大量 IO，死循环等。ANR 会导致主线程卡死，不会直接抛出业务异常。

## 14. 如何对 App 进行性能优化

- 启动速度优化：减少 Application 里面的做的事情，减少首屏布局复杂度，避免主线程堵塞。
- 界面流畅度优化：避免主线程做耗时操作，优化布局层级，减少布局嵌套，列表优化，减少绘制，优化动画
- 内存优化：避免内存泄漏，单例要使用 applicationContext，减少大对象和频繁创建对象，优化图片，降低图片采样率，按需加载，使用 glide 第三方库，及时清理不需要的图片引用。
- 网络优化：接口合并，减少请求次数，分页加载，缓存数据，减少重复请求，设置合理的超时机制和重试机制。
- 耗电优化：减少不必要的轮询，减少频繁唤醒 CPU，定位，蓝牙，传感器按需开启。
- 包体积优化：删除无用的资源，删除无用的引用，图片压缩。

## 15. 用户在浏览器输入网址，然后网址展示给用户，整个过程是什么

用户输入 URL 后，浏览器先解析 URL 并进行 DNS 解析得到 IP，然后建立连接（TCP 三次握手，HTTPS 还要 TLS 握手），接着发送 HTTP 请求，服务器处理后返回响应。浏览器收到 HTML 后解析生成 DOM 和 CSSOM，构建渲染树并进行 layout 和 paint，合成后显示页面，同时继续加载 CSS/JS/图片等资源并执行脚本，最终页面可交互。

## 16. https 和 http 的区别，为什么要选用 https，ca 证书工作的原理。

http 是明文传输，https 是加密传输，http 的端口是 80，https 的端口是 443，https 需要做 TLS 握手，加解密，证书校验。https 可以防止抓包，中间人攻击，https 可以配合 CA 证书，可以让客户端校验证书是否合法，从而判断服务器身份是否可信。CA 证书是一个可信的第三方担保机构。CA 证书的原理是服务器先向 CA 申请证书，CA 审核后用自己的私钥对证书进行数字签名。客户端访问服务器时会收到证书，再用本地信任的 CA 公钥验证签名、校验证书有效期和域名是否匹配。验证通过后，客户端和服务器再协商对称密钥，后续用对称加密进行高效安全通信。

## 29. 你知道哪些设计模式

### 1. 单例模式 (Singleton Pattern) 的不同实现

**项目背景：** 项目中同时使用了 Java 和 Kotlin 编写的类，并且都有单例模式的体现。例如 Java 编写的数据库类 `AppDatabase` 和 Kotlin 编写的单例对象 `ApiRepository`。

- **提问：** “我看项目中获取 `AppDatabase` 实例时，使用了带有 `volatile` 关键字的双重检查锁（Double-Checked Locking）机制。但是在 `ApiRepository` 和 `PrinterManager` 中，直接使用了 Kotlin 的 `object` 关键字。你能解释一下这两者的区别吗？Kotlin 的 `object` 是如何保证线程安全的？”
- **考察点：** 多线程并发知识、Java 与 Kotlin 底层机制的理解。
- **期望回答：**
  - Java 中的双重检查锁是为了在多线程环境下，既保证只创建一个实例，又避免每次获取实例时都加锁带来的性能损耗；`volatile` 是为了防止指令重排导致拿到未初始化完全的对象。
  - Kotlin 的 `object` 关键字在编译成 Java 字节码后，本质上是通过静态代码块（饿汉式）来实现的。它的线程安全性是由 JVM 在类加载阶段的机制来保证的，开发者无需手动编写同步代码。

### 2. 观察者模式 (Observer Pattern) 与响应式编程

**项目背景：** 项目的 UI 层使用了 MVVM 架构，`Main.kt` 中大量使用了 `observe` 来监听 `MainViewModel` 中的数据变化。

- **提问：** “在 `Main.kt` 中，我们通过 `viewModel.productList.observe(...)` 来更新 UI。这在底层其实是运用了哪种设计模式？相比于传统的回调接口（Callback），这种模式在 Android 开发中有什么核心优势？”
- **考察点：** 观察者模式的概念、对 LiveData 及生命周期的理解。
- **期望回答：**
  - 这运用了**观察者模式**。`LiveData` 是被观察者（Subject），Activity/Fragment 是观察者（Observer）。当 `ViewModel` 中的数据发生变化时，会自动通知观察者更新 UI。
  - 核心优势在于**生命周期感知**和**解耦**。LiveData 知道 Activity 的生命周期状态，只有在界面处于可见活跃状态时才会触发回调，自动避免了因为 Activity 销毁后仍在更新 UI 而导致的内存泄漏和崩溃 Crash 问题。

### 3. 外观模式 (Facade Pattern) / 仓储模式 (Repository Pattern)

**项目背景：** 网络请求相关的逻辑都被封装在了 `ApiRepository.kt` 中。

- **提问：** “所有的 Retrofit 网络请求操作（如 `NetworkManager.cameraApi.xxx`）并没有直接写在 ViewModel 里，而是统一定义在了一个名为 `ApiRepository` 的单例对象中。从架构设计模式的角度来看，这样做的目的是什么？”
- **考察点：** 外观模式/仓储模式、单一职责原则。
- **期望回答：**
  - 这体现了**外观模式**（为子系统中的一组接口提供一个一致的界面）和**仓储模式**（隔离数据层和业务层）。
  - **目的**：ViewModel 不需要关心数据是从网络获取的（Retrofit）、底层是如何进行异常捕获的（`try-catch ApiException`），甚至未来如果加入本地缓存，ViewModel 也不需要改动。`ApiRepository` 提供了一个干净的门面，向外统一返回 `NetworkResult` 密封类（Success/Error）。符合单一职责原则，让代码更容易测试和维护。

### 4. 适配器模式 (Adapter Pattern) 在 UI 中的应用

**项目背景：** 主界面商品列表的展示使用了 `RecyclerView` 和 `ProductItemAdapter`。

- **提问：** “除了我们之前讨论的抽象不同厂家的打印机 SDK 会用到适配器模式，在 Android UI 开发中，`ProductItemAdapter` 也是适配器模式的典型应用。你能说说在这个场景下，谁是需要被适配的源（Adaptee），谁是目标接口（Target）吗？”
- **考察点：** 对常用 Android 组件设计思想的深度理解，而不仅仅是会写代码。
- **期望回答：**
  - **源（Adaptee）**：是我们从后台获取到的、结构各异的业务数据集合（比如 `List<Product>`）。
  - **目标接口（Target）**：是 `RecyclerView` 控件所期望的、能直接渲染到屏幕上的 View 视图对象。
  - **适配器的作用**：`RecyclerView` 作为一个通用的列表控件，不可能知道我们的业务数据长什么样。`ProductItemAdapter` 的职责就是将业务数据（Product 模型）“翻译” / 绑定到具体的 UI 布局文件上，从而完成数据到视图的适配转换。
